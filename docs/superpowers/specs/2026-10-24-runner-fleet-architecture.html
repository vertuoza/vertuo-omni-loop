Omni Loop · mini project

Runner fleet

Four machines that do one thing: run coding agents for the loop. The Omni Loop server hands them work. They open pull requests on GitHub or send their work back to Omni, and they report every token, every approximate dollar and every gigabyte as they go.

Inside a runner

One machine, seven layers

The same stack on all four machines. The top layer is the omni runner process the kit already ships; the layers in cyan are what this project adds.

The runner processNew in this projectIn the kit today

Runner

Holds the connection to Omni, takes leases, runs each job in its own worktree and tmux session, releases claims when a job ends.

omni runner --name atelier-01 --slots 2

Agent adapters

One interface over every CLI: start, resume, stream its steps, read its usage. Claude Code and Codex first; any CLI that prints its usage can join.

claude · codex · gemini

Account pool

One signed-in account per CLI, each with its state (ready, active, out until a reset time) and the order to turn over in.

~/.config/omni/accounts.yml

Job journal

Written at every step: the job, its worktree, branch, last pushed commit, agent session and a handoff note. Read first on boot.

~/.omni/runner/journal/<job>.json

Meter and health

Samples CPU, load, memory and disk; counts tokens per model. Today it sends tokens; with a price list it also sends an approximate cost.

health line · PRD 2102

Toolchain image

One reproducible image, the same on the office machines and on Hetzner, rebuilt when a repository needs a new tool.

mise · Docker · cloud-init

Network

Tailscale joins the machine to the tailnet with every inbound port closed. The runner only ever dials out.

tailscale up --ssh
Flows

A job, a turnover, a restart

The three sequences the runner has to get right.

A job, end to end

From Send to a pull request

  1. Someone presses Send to terminal on the Omni page, an API key calls, or /omni:drive starts a step.
  2. Omni queues the job. A runner that holds the repository, has a free slot and an account with tokens left takes a lease on it.
  3. The command arrives on the runner's open connection: the line, the repository and the preferred CLI.
  4. The runner makes a fresh worktree, opens tmux session job-<id> and starts the agent.
  5. Every 15 seconds it reports the step, the model, the tokens, the cost and its health. The lease is renewed with each report.
  6. The job ends with a pull request on GitHub, or with its work on Omni: outbox items, a proof, a dossier. The worktree is removed.
Turnover

When an account runs out

  1. The meter sees the CLI's own signal: a usage-limit message, the plan's 5-hour or weekly window, or the budget set for that account.
  2. The runner marks the account out, with its reset time, and sends no new turn to it.
  3. It checkpoints the job: commits and pushes the branch, writes the journal and a handoff note of what is done and what is next.
  4. It starts the next CLI that has tokens, in the same worktree, with the handoff note as its first message.
  5. The report names the turnover, so the job shows which model did which part and what each part cost.
  6. At the reset time the account reads ready again, and new jobs start on the preferred CLI.

When every account is out, the runner reads Paused: no tokens. It takes no new job, and Omni sends work to the other runners.

Restart

Picking jobs back up

  1. The runner starts and reads its journal before it asks for new work.
  2. For each job in the journal, it asks Omni to renew the lease. If Omni already gave the job to another runner, it drops its copy.
  3. Otherwise it reopens the worktree on the last pushed commit and resumes the agent's session (claude --resume, codex resume).
  4. If the session is gone, it starts the agent fresh with the handoff note.
  5. The job's row on the Runners page reads Resumed, with how long it was down.

A runner that never comes back, a reclaimed Hetzner machine for instance, goes quiet. After 90 seconds its lease expires and the job returns to the queue with its pushed branch, for any runner that holds the repository.

Cost is an estimate

Tokens are counted exactly; cost is tokens times the public list price of the model, kept on the server so one price change applies to every runner. On a subscription account it reads as what the same work would cost through the API.

The report is the heartbeat

Each report renews the runner's leases. No report for 90 seconds and its jobs go back to the queue, which is what makes a Hetzner machine that disappears safe.

Secrets never leave

Tokens of the accounts stay on the machine. The report names an account by its CLI, and the runner masks every secret in the lines it streams, as it already does for a GitHub App token.

Open questions

Five answers that would change the drawing

Each shows the choice the page assumes, so the drawing can stand until it is answered.

Does a job turn over mid-way, or only between jobs?

Moving from Claude to Codex in the middle of a job keeps it going but mixes two models' work in one pull request.

Assumed: mid-way, at a checkpoint, with a handoff note.

Does Omni push commands, or do runners keep dialling out?

With the Omni server on the tailnet it could reach runners directly; dialling out works behind any firewall and keeps today's model.

Assumed: runners dial out and hold the connection.

What does low availability mean on Hetzner?

Machines that can be reclaimed at any time, machines switched off at night to save money, or both. It decides whether the fleet should start and stop them itself.

Assumed: they can vanish without warning.

Whose accounts are they?

One set of accounts per runner, or one pool the server hands out so a second runner never uses an account that is already out.

Assumed: one set per runner, as you described.

Which cost does the page show?

On a subscription plan nothing is billed per token. The page can show the list-price equivalent, or a share of the plan's monthly price.

Assumed: the list-price equivalent, labelled approximate.
