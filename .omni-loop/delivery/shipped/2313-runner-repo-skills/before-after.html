PRD 2313: before and after

A repository allows its own skills on a runner, from Settings › Repositories.

galaxy

Functional

Today
  1. A repository's own skill, /validate-prd, runs only by hand, on someone's laptop.
  2. Send to terminal refuses /validate-prd 347: a line must read /omni:<skill>.
  3. Settings › Repositories shows the repository's switches, and nothing about its skills.
After
  1. An owner opens Runner skills under the repository and sees every skill on its default branch, with its description.
  2. They turn Allow on runner on for /validate-prd. The line reads "allowed by @ada on 21 Oct".
  3. Any member sends /validate-prd 347 from Send to terminal. A runner holding the repository runs it, with the repository's MCP servers loaded.
  4. A skill that leaves the default branch reads Gone, and a job sent for it fails before it runs.
  5. A skill nobody allowed is refused when it is sent: "an owner allows it in Settings › Repositories."

Flow

Deploy order

  1. supabase: the migration (the table and two functions). Every list reads empty, so nothing changes yet.
  2. galaxy: the Runner skills block, the line check, queue(), the claim sending allowedSkills.
  3. kit: the next v0.0.N release. A runner on an older kit ignores allowedSkills and still refuses every /<name> line. A newer kit reads a job without it as [].

No coordinated deploy: each step works with the one before it alone.

Behaviour

Today
  • queue() refuses any line off the fixed list.
  • answer() resumes any job with questions.
  • sendable(line) (Send to terminal) knows the fixed list only.
After
  • queue() reads repository_runner_skills_of() and takes an allowed /<name>.
  • answer() refuses a repository-skill job; dismissing still works.
  • sendable(line, allowed). prdOfLine ignores repository skills, and linePrd lists them under the PRD of their first argument.
