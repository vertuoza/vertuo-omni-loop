PRD 2305: before and after

repository

Functional

Anyone reading the public code today finds the maintainer's other repositories, colleagues' emails and the maintainer's plan repository in about a thousand files, mostly test fixtures and the loop's history. After, they read fictional ones: demo-org, nimbus-*, @example.com.

Today (shape, not the real values)
repo: '<maintainer org>/<internal repo>'email: '<colleague>@<maintainer domain>'"name": "<maintainer plan repository>"
After
repo: 'demo-org/nimbus-core'email: 'ada@example.com'"name": "omni-loop"

A contributor today can add an internal name, a real email or a key and nothing notices. After, the pre-push hook and CI refuse it with the file, the line and what to write instead; gitleaks scans every pull request's commits for secrets.

Today
$ git push… pushed: a fixture naming another internal repository,  a colleague's real email, or a key, goes public unnoticed
After
$ git pushopen-source: kit/lib/foo.test.ts:12: internal repository — use demo-org/nimbus-<name>open-source: apps/galaxy/src/x.ts:40: real email — use <name>@example.compush refused · node scripts/open-source.ts

supabase

Functional

Someone self-hosting Omni Loop today gets the maintainer's workspace and repositories on a fresh database. After, a fresh install has no workspace from the migrations; the demo seed brings its own demo-org. Production is untouched.

Today
$ supabase db resetworkspaces: the maintainer's workspace  + its repositories and sectorsseed: the demo galaxy, inside it
After
$ supabase db resetworkspaces: none from the migrationsseed: a demo-org workspace and its demo galaxy

Flow

Deploy order

One feature PR. The guard lands first with its baseline; the cleanup slices empty it; the last slice deletes it. The edited migrations are never re-run in production (applied by version, not content), so nothing is ordered against the database. Builds after PR #2304 merges.
