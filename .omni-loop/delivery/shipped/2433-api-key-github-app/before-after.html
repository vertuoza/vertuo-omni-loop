PRD 2433: before and after — a key's job runs as its own GitHub App

galaxy

Functional

TODAY
  • An app that sends a bug fix with its key gets a pull request that GitHub shows as a person's work: the account of whoever set up the runner's machine. The bug's issue, its comments and labels, the branch, the commits and the pull request are all theirs.
  • That person neither asked for the fix nor reviews it, yet GitHub notifies them and counts the work as theirs.
  • The pull request's body pings the key's maker, in a broken line: Sent from the Omni app by @API key QA dashboard (@ada) on runner mac-mini-1.
  • When the job ends, its claims are released (a label swapped, a comment on each pull request) as that same person.
  • Settings › API keys lists each key's name, maker, repositories and last use. It says nothing about GitHub.
AFTER
  • An owner attaches the app's GitHub App to a key, once, on Settings › API keys: its App ID and its private key file. Omni asks GitHub to confirm the pair before it keeps anything. The private key is never shown again, to anyone.
  • Every member reads, on each key's row, which GitHub App the key runs as. An owner also reads when it last got a token, and can replace or remove the app. Revoking the key, or removing the app, deletes the stored private key.
  • Everything the job writes on GitHub is the app's bot: the bug's issue, its comments and labels, the branch, the commits, the pull request, its status comment and the release of its claims.
  • No person is named, assigned or asked for a review by the job: no assignee, no review request, no @login. A CODEOWNERS file still asks its owners: that is the repository's own rule, outside the job. The commits carry the agent's own Co-Authored-By and Omni-man's line, never a member's.
  • The pull request's body reads Sent through the Omni API by API key QA dashboard on runner mac-mini-1. So does any key job's, with or without an app. A person's job from the Runners page keeps Sent from the Omni app by @ada on runner mac-mini-1.
  • Sending to a repository where the app is not installed, or where it lacks write access to contents, pull requests or issues, is refused with a message naming the repository or the permission. Nothing is queued.
  • A job whose token cannot be minted when a runner takes it ends failed with github app: <why>. It never runs under a person's account, whether the app was removed or uninstalled, the key revoked, or its maker left the workspace.
  • A key with no app works as today, save the sender line.

Flow

Deploy order

  1. supabase: the migration <version>_api_key_github_apps.sql (the table, its two functions, the keys list's new fields, the revoke that deletes the row), applied by the supabase workflow on merge, with its check supabase/checks/api_key_github_apps.sql. It ships first: galaxy reads the table and calls the functions.
  2. galaxy: the settings routes, the send-time checks, githubApp at register, github and sentByKey at claim, the refresh route and the page, deployed by the release that follows. It must run before any runner takes the new kit: RegisterRequestSchema is strict, so a galaxy that does not know githubApp refuses that runner's registration.
  3. kit: the release v0.0.N with the runner's app identity and the skills' new text; each runner takes it with omni update. A runner on an older kit keeps working, registers no githubApp and never claims a job of a key with an app.

Rollback: revert the merge. Keys lose their app, jobs of such keys send as today, and a follow-up migration drops the table.

Behaviour

TODAY · runners.service.ts, public-api.service.ts
  • POST /api/v1/bug-fixes checks the key and its allow-list, then queues the job.
  • next hands a queued job to any online runner with a free slot that holds the repository.
  • A claimed job is {id, line, repo, sentBy, allowedSkills}; for a key's job senderOf writes sentBy as API key <name> (@<login>).
  • No route mints a GitHub credential for a job. Omni knows one GitHub App, its own.
AFTER
  • Attach: checks the pair with GitHub (an app JWT, GET /app, then GET /users/<slug>[bot]) before storing anything, seals the private key with the secret box under SECRETS_MASTER_KEY, then calls api_key_github_app_attach. A pair GitHub refuses, or a deployment with no master key, is refused and stores nothing.
  • Send: for a key with an app, finds the app's installation on the job's repository (the plan repository for a mega) before queuing, and reads its permissions. No installation, or no write on contents, pull_requests or issues: 422, nothing queued.
  • Claim: a job of a key with an app goes only to a runner that registered githubApp: true. Galaxy then mints an installation token for the job's repository (for a mega, the plan repository and every repository its product names that the installation holds, within the key's allow-list), with contents, pull_requests and issues write and metadata read, and nothing more. The claim gains github and sentByKey; a job with no app gets github: null, a person's job sentByKey: null. The mint is recorded in last_token_at.
  • No mint, no person: when the token cannot be minted at claim (an app removed or uninstalled, a pair GitHub now refuses, a key revoked, a maker who left the workspace, a master key lost), the job ends failed with github app: <why> and no runner runs it. A job queued while an app was attached keeps needing one: removing the app does not send it as a person.
  • Refresh: POST /api/runners/jobs/<id>/github-token mints a fresh token for the job's runner only, and records the mint.
  • The keys list answers githubApp to every member and lastTokenAt to an owner; revoking a key also deletes its stored private key.
