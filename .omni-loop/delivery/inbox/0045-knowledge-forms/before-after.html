Omni knowledge forms

vertuo-ai-domain writes down two kinds of knowledge. docs/knowledge/ says what is true about the product. docs/agents/ says how to work in the repository: how to test, how CI works, when a pull request is done. Omni already carries the first kind. This PRD adds the second: fixed forms inside .omni-loop/knowledge/, a /omni:terraform skill that fills them from the repository, and a pointer wherever the repository already has the page.

pointer the repo already has it filled from evidence partial filled, with holes kit default nothing repo-specific hole a question for a person

Before and after

Today

  • .omni-loop/knowledge/ holds only the truth registers: principles, rules, invariants and ADRs. PRD #3 ported them from ai-domain.
  • How-to knowledge is one optional free-text file, .omni-loop/repo.md. do-work reads it "when it exists". It does not exist in this repository.
  • paths.context defaults to CLAUDE.md. This repository has none, so do-work starts with no repo context.
  • The skills stay generic. do-work knows the test command as one config string. pr re-runs a red check without knowing which reds are already known.
  • When ADRs live elsewhere, only paths.adr knows about it. A person who opens .omni-loop/knowledge/adr/ finds no link to them.
  • Nothing grades this guidance, so a stale "how to test" looks the same as a current one.

With the forms

  • knowledge/playbook/ holds one form per question an agent asks while delivering: 8 core forms and 5 extended ones.
  • Every form has a fixed shape, taken from ai-domain's docs/agents/ pages. Its sections are slots, and a person fills in the ones the skill could not.
  • The kit ships a default for every section. A filled repo section overrides the default, and a pointer overrides both.
  • When the repository already has the page, the form points to it. adr/README.md says where the ADRs are.
  • /omni:terraform fills the forms from evidence: scripts, workflows, configs and existing docs. A command is written only after it has run green.
  • omni check kb fails on a dead pointer. It warns on a blank slot, an open question or stale evidence.
  • Each skill reads omni kb show <form> at the step that needs it.

The folder

.omni-loop/knowledge/ is always the front door, even when the knowledge lives somewhere else. Anything kept elsewhere gets a pointer here, so a person or an agent always starts in the same place.

The two commands

One command lays down the empty forms. The other fills them from what the repository can prove.

omni kb init · creates the forms

  • A plain CLI command, with no AI involved. Safe to run again.
  • Writes every missing form from the kit template with state: blank, its opener and its slot hints.
  • Writes knowledge/README.md and adr/README.md when they are missing, and the three empty product/ register files when there are none, so omni check knowledge stays green.
  • Never overwrites a file.
  • omni init (PRD #39, the one-line install) runs it too, right after the config and the bin. Its closing steps then point to /omni:terraform.

/omni:terraform · fills them from the repo

  1. Check it is installed (omni config; otherwise omni init comes first), then run omni kb init. Survey, read-only: scripts, lockfile, engines, test configs, workflows, PR template, CODEOWNERS, labels, hooks, README, CLAUDE.md or AGENTS.md, docs/.
  2. Point before writing. If a page already answers a form's question, the form becomes a pointer.
  3. Fill from evidence. Each filled section lists its files under evidence:. Each command runs green once before it is written down.
  4. Leave holes. Anything it cannot show becomes TODO(human): <question>.
  5. Propose config as a diff. omni init already detected the commands, so terraform runs each one and proposes a change only where one is missing or fails. It also proposes paths.adr, paths.glossary, paths.context and ci.aggregateCheck.
  6. Open a docs-only PR whose body lists every hole as a checkbox. A person fills them in and merges.

--refresh redoes only the forms whose evidence changed, and never touches a by: human section.

Fails the check

  • A points-to:, See: or evidence: path that does not exist
  • A slot id the form does not define, or a missing required heading
  • A form-version newer than the installed kit

Warns, never fails

  • A TODO(human) still open
  • A required slot left blank, so the kit default applies
  • Evidence changed since the form was filled. A week later that reads:
    testing.md · stale · vitest.config.mjs changed since 2026-09-25 → /omni:terraform --refresh

Decided

The brainstorm left six questions open, each with a recommendation. The PRD author approved all six on 25 September 2026. Two more came from re-planning after PRD #39 merged. The spec lists all of them with its other decisions.

  1. Where the forms liveDecided: .omni-loop/knowledge/playbook/, under the one knowledge root, through a new paths.playbook key that defaults there. Its parent is the front door.
  2. Whether a hole blocks deliveryDecided: it does not. omni check kb warns, and /omni:yolo prints the holes once at the start and uses the kit defaults.
  3. Pages or generated skillsDecided: pages, read by the one omni plugin. Per-repository skill copies are the drift PRD #3 was written to end.
  4. How fine-grained pointers areDecided: both levels. A whole form can be state: pointer, and a section can carry a See: line.
  5. Process lessons from settled outbox answersDecided: they land in a playbook section, by: human, and the settled entry records Became: playbook/<form>#<slot>, which omni check outbox resolves.
  6. Orientation pagesDecided: later. A form points to them when they exist.
  7. The one-line install lays down the formsAdded after PRD #39 merged, for the phase-0 review: omni init writes the blank forms after the config and the bin, and its closing steps name /omni:terraform. Installing is one command, and filling the forms is one skill.
  8. A knowledge folder no longer means lawsAdded after PRD #39 merged, for the phase-0 review: every install now creates .omni-loop/knowledge/, so omni init reads laws.source: knowledge from registers that hold an entry, not from the folder existing.
