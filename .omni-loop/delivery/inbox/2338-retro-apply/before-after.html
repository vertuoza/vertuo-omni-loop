kit

Functional

TODAY

A retro keeps a lesson and opens a retro issue. Its last block says it is "for /omni:retro-apply to read", but that command does not exist. The lesson stays in the retro's files and its issue. No agent reads it while building, and nothing says yes or no to it.

The same lesson can come back retro after retro: "regenerate the database types, never hand-edit them" came back three times (#1349, #1649, #2207) before a person wrote the rule by hand.

AFTER

/omni:retro-apply --retro <retro PR> settles every kept lesson of that retro on its own pull request:

  • Becomes a rule: the rule is added to the playbook form it belongs in, and the retro PR quotes it word for word with its place.
  • Stays here: a rule already says it, or it is not about how to work here; the retro PR says why.
  • Asks: when it cannot tell, it asks one question on the retro PR and settles nothing.

omni check retro keeps the retro PR red until every kept lesson has an answer. With retro.guards switched on for the repository, a lesson worth it also gets a guard test.

Flow

Deploy order

  1. The migration (runner_jobs.sent_by_app), through the supabase workflow.
  2. galaxy: the Runners page reads an app-sent job.
  3. The kit (the skill, RUNNABLE_SKILLS, omni check retro): a runner updates its plugin before a job.
  4. omni-app: the retro queues the job. Last, so no job is queued before a runner can run it and the page can show it.

One merge ships them all; the release commit deploys galaxy and omni-app after the migration has run.
