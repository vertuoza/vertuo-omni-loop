PRD 2898: before and after

kit

Functional

Today

In a mission, the Reviewer reads the feature pull request and, when it finds nothing, marks it ready (PRD 2871). Nothing proves what that ready stands on: CI may still run, or may have run only the tests of the changed files; a test may have been skipped to go green; a file outside every slice may have changed.

A spec's acceptance criteria are plain bullets: nothing ties one to the test that proves it.

After

Before the Reviewer marks a mission's pull request ready, it asks omni ready. Ready only when five checks pass on the latest commit: CI green, the full tests and lint ran, every acceptance criterion has its proof, no test was loosened, the change stayed in its area. One check short, the pull request stays a draft and the Reviewer asks for changes, naming the failing check.

A check still waiting on its evidence never passes. A loosened test or a file outside the plan is excused only by an outbox item a person answered (a file outside the plan also by an adopted medium item).

A spec writes each criterion as a numbered scenario, Given, When, Then, with its kind: test (a test of the same name) or e2e (run against the pull request's preview). omni check inbox refuses a criterion with a number missing or twice, no kind, or no Given, When or Then.

Who is gated is one setting: missions only here, off by default, every feature PR later with no new code. Outside a mission nothing changes.

omni-app

Functional

Today

The App posts its own checks on a pull request (the outbox, the budgets). None says whether a ready pull request is proven.

After

On every new commit of a gated pull request, the App runs the same five checks and posts the check omni / ready: each check's state with a link to its evidence, signed as the App's. It keeps the verdict for the PRD page.

When e2e does not run in CI, a runner of the workspace runs the scenarios against the preview, and the App writes their results on the commit. When the App cannot be reached, omni ready still decides alone.

galaxy

Functional

Today

A PRD's page shows its feature pull request as ready and its CI chip. To trust it, a reviewer asks an engineer or reads the whole diff.

After

A Ready panel on the PRD's page shows the latest verdict: Ready for review · 5 of 5, or 4 of 5 with the failing check named at the top. Each check is one tap from its evidence; each acceptance criterion shows its three lines, its kind, its proof and its state. Then: Ready for review, not merged. Only a person merges. and Review PR <n>.

A check still running reads Waiting and never counts as passed.

supabase

Functional

Today

Nothing keeps what a ready pull request was checked against.

After

Each verdict the App reaches is kept, one per commit of a pull request: the five checks and whether it passed. Members of the workspace read them; only the App writes them.

Flow

CI is not a service of the architecture form: its jobs show here and in Deploy order. The model provider is the one e2e.model names.

Deploy order

On a gated draft, the skill adds the label omni:ready-check before omni ready: the label starts the full checks, the e2e job and the preview on the draft's latest commit (.github/workflows/checks.yml, preview-debounce.yml).

  1. supabase: the migration creating public.ready_verdicts and its policies, with its supabase/checks/.
  2. omni-app: the omni / ready check and the runner fallback writing acceptance; it posts nothing while ready.checks is off.
  3. CI: the full checks, the e2e job and the preview on a draft labelled omni:ready-check, the test job's AC report, the e2e job on the preview, the acceptance check run (E2E_TELEMETRY_DISABLED=1, the model key a secret).
  4. kit: the validator, omni ready, the settings, the AC format in omni check inbox, then the skills (/omni:review's gate line, /omni:validate-e2e, /omni:brainstorm).
  5. galaxy: the Ready panel on the PRD page.
  6. Switch on: ready.checks stays off until all of the above are out, then mission. Roll back with off.

Pixel perfect

screens: prd-dossier · ready-checks · app-shell

The Ready panel is the library screen ready-checks, drawn as a panel of the PRD page (prd-dossier) inside the app shell, at 1280 px, theme Omni. PRD 2803 and PR 2817 stand in for any mission PRD; the PRD's own text is marked data-content.

1.A · A mission PRD whose PR the Reviewer marked ready

Today: the page says Feature PR · ready and CI green, nothing more. After: the Ready panel sits under the head, above the tab shown, while the feature PR has a verdict; check 3 lists each criterion with its three lines, its kind, its proof and its state. The panel's own style is a hole in dossier.css: it is filled from the business laws' verdict (.dossier-laws), the Proof tab's rows (.proof-row) and the PR care chip, in the Ask tokens; a failing mark takes red as the Proof tab does. Signed as the App's (L-AIACT-1); the one primary action is Review PR 2817.

1.B · 4 of 5: a test was loosened

The failing check is named at the top, with the file and why. The pull request stays a draft: the stage stays at building, the Reviewer ended changes. Its primary action opens the evidence.

1.C · Waiting: the evidence is not there yet

A check still running, or an e2e scenario no runner has run, reads Waiting and never counts as passed (BL-GATE-1). The words omni ready prints for check 3 (waiting for a runner to run the e2e scenarios) are cut to waiting for a runner by the word pass; AC-3 shows which scenario waits. A check that could not read its evidence reads Not judged · <why> in the same place, not drawn here.
