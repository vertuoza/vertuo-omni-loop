Knowledge Harvest

When a feature PR merges, what its PRD decided goes into the knowledge base: as a decision record, an invariant or a business rule, in the right place, with who answered, who merged and when. Today it stays in a ledger nobody reads.

The ledger entries and counts are real, from this repository. The merged-over-red PR, merge dates, logins and new ids are illustrations.

How it runs, in the omni-loop app

The files are read from main as it is when the run starts; the merge commit only gives the provenance. One run at a time per repository, so two knowledge PRs never take the same id. The same kit units run locally as omni harvest <prd> --pr <n>, which is how one slice fills this repository's knowledge base from the six PRDs already shipped.

What changes, what stays

Changes

  • A merge over a red outbox adopts what is still open, in the merger's name, and ships the folder.
  • Every settled decision ends with Became: or Stays here:, or is listed as not placed for a person.
  • Knowledge entries carry Decided:, Merged: and a Source: naming the ledger entry.
  • The retro always writes into shipped/, and shares its model client and git writer with the harvest.
  • Two config keys: branches.knowledge and labels.knowledge.

Stays the same

  • Medium items are adopted when raised, and only for information.
  • No bot writes to main: a person merges every knowledge PR.
  • An existing entry is never edited, no domain is created, and nothing is confirmed by a merge.
  • /omni:yolo-fix's write-back works as today; the harvest skips what it already wrote.
  • The outbox check, the manifest beyond PRD 72's permissions, and every installed repository: nothing is added there.
